Most technology strategy is written for the moment it's adopted. I'm more interested in the moment it's tested — when the pilot has to reach production, when the architecture has to survive the outage, when the compute bill lands on the board's desk. That's where technology stops being a roadmap and becomes a consequence.

That's what I write about at [deepakwaghmare.com](https://deepakwaghmare.com): organizational resilience and what a company discovers is actually load-bearing only in a crisis; the economics of compute, where efficiency is quietly overtaking raw capability as the real constraint; and technology sovereignty as a category rather than a slogan. Across the whole enterprise stack — infrastructure, data, and AI — not one fashionable layer of it. Two books are in progress along those lines: *The Token Trap* and *The Load-Bearing Core*.

This GitHub is the workbench behind the writing — benchmarks, reference builds, and the code I use to check an argument before I make it in public. I've never trusted a claim I couldn't run.

### What lives here

- **[vexpose-labs](https://github.com/waghmaredb/vexpose-labs)** — the working code behind [vExpose](https://www.vexpose.blog): benchmarks, reference architectures, and the scripts I use to check my own numbers before publishing.
- **Infrastructure-as-code reference builds** — Kubernetes, OpenShift on bare metal, and storage automation from years spent closer to the metal. Kept public because someone always needs a working example.
